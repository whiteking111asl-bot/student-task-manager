# Перевірка вимог Student Task Manager

## Джерела й обсяг

Перевірено 5 функціональних і 3 нефункціональні вимоги з ПР7 (коміт `a1d2a03`). Джерела для звірки меж MVP — [опис продукту](product-description.md) і [план розробки та зведення backlog](../README.md). Остаточні формулювання й тести наведені у [requirements.md](requirements.md).

## Результати по вимогах

### FR-01 · Створення завдання

**Було.** Система повинна дозволяти користувачеві створити навчальне завдання, указавши обов'язкову назву, дисципліну та дату здачі.

**Виявлено.** Початкова вимога визначає поля, але не визначає початковий статус. Це залишає результат створення неоднозначним.

**Стало.** Після збереження форми з непорожньою назвою, дисципліною та допустимою датою здачі система повинна створити одне завдання зі статусом «Не виконано».

**Як перевірити.** Подати форму з назвою «Звіт», дисципліною «Інформатика» та датою 2026-11-20. Має з’явитися рівно один запис із цими даними та статусом «Не виконано».

### FR-02 · Перегляд списку завдань

**Було.** Система повинна відображати користувачеві список збережених завдань із назвою, дисципліною, датою здачі та поточним статусом кожного запису.

**Виявлено.** Початкова вимога атомарна, але не описує порожній список. Уточнено цей стан і прибрано суб’єктивне «правильно» з перевірки.

**Стало.** Система повинна показувати в списку всі збережені завдання з назвою, дисципліною, датою здачі та поточним статусом кожного. Для порожнього списку відображається повідомлення «Немає завдань».

**Як перевірити.** Відкрити список із двома різними завданнями і звірити чотири поля кожного. У порожньому сховищі має з’явитися повідомлення «Немає завдань».

### FR-03 · Редагування завдання

**Було.** Система повинна дозволяти користувачеві змінити назву, дисципліну або дату здачі раніше створеного завдання.

**Виявлено.** Початкова вимога перелічує дозволені поля, але правило збереження незмінених полів є лише в прикладі тесту. Перенесено його в основний текст.

**Стало.** Система повинна дозволяти студенту змінити назву, дисципліну або дату здачі вибраного завдання. Після збереження змінюються лише відредаговані поля.

**Як перевірити.** Змінити дату одного з двох завдань. Нова дата має з’явитися лише в обраному записі, а решта значень, зокрема його статус, має зберегтися.

### FR-04 · Позначення виконання

**Було.** Система повинна дозволяти користувачеві змінювати статус завдання з «Не виконано» на «Виконано» та відображати новий статус у списку.

**Виявлено.** Відображення поточного статусу вже описане у FR-02. FR-04 залишає одну дію — зміну статусу. Список використовується для перевірки результату.

**Стало.** Система повинна дозволяти студенту змінити статус вибраного завдання з «Не виконано» на «Виконано».

**Як перевірити.** Позначити одне з двох невиконаних завдань як виконане. Звірити, що змінився тільки статус вибраного запису.

### FR-05 · Сортування за строком здачі

**Було.** Система повинна дозволяти користувачеві впорядковувати список завдань за датою здачі від найближчої до найпізнішої.

**Виявлено.** Не визначено поведінку для однакових дат. Правило робить результат передбачуваним. Позначку поза MVP збережено.

**Стало.** Після вибору сортування за строком здачі система повинна впорядкувати завдання за датою від найранішої до найпізнішої. Завдання з однаковою датою зберігають попередній взаємний порядок.

**Як перевірити.** Увімкнути сортування для записів A, B, C з датами 2026-11-21, 2026-11-20, 2026-11-21. Очікуваний порядок — B, A, C.

### NFR-01 · Збереження даних

**Було.** Створені завдання та зміни їхніх даних повинні зберігатися після закриття й повторного запуску застосунку на тому самому пристрої.

**Виявлено.** Початковий тест перевіряв лише один запис і статус. Уточнено умови перезапуску та поширено перевірку на редаговані дані.

**Стало.** Після штатного закриття й повторного запуску на тому самому пристрої список завдань повинен містити всі успішно збережені записи з їхніми останніми значеннями.

**Як перевірити.** Створити два завдання, змінити дату першого і статус другого, штатно закрити й відкрити застосунок. Звірити обидва записи та всі поля.

### NFR-02 · Цілісність даних при введенні

**Було.** Система не повинна зберігати завдання, якщо назва порожня або дата здачі має некоректний формат; користувач повинен бачити повідомлення про відповідне поле.

**Виявлено.** Початковий текст не покривав обов’язкову дисципліну з FR-01, не визначав формат дати та допускав різні тлумачення щодо редагування. Повідомлення залишено як спостережувану ознаку тієї самої відмови.

**Стало.** Після спроби зберегти форму з порожньою або пробільною назвою чи дисципліною або з недопустимою датою система повинна залишити сховище без змін. Допустима дата — наявна календарна дата у форматі YYYY-MM-DD. Повідомлення має вказувати кожне некоректне поле.

**Як перевірити.** Окремо перевірити пробільну назву, порожню дисципліну та дату 2026-02-30 під час створення й редагування. Записи мають лишитися без змін, повідомлення має назвати відповідне поле.

### NFR-03 · Час відкриття списку

**Було.** На пристрої з 100 збереженими завданнями список повинен відкриватися не довше ніж за 2 секунди після вибору відповідного екрана.

**Виявлено.** Поріг уже був вимірюваним. Уточнено межі вимірювання та умови відтворення. Вимога залишається поза MVP.

**Стало.** У кожному з п’яти відкриттів екрана списку час від вибору екрана до показу всіх 100 локально збережених записів має становити не більше ніж 2 секунди. Вимірювання виконуються на одному тестовому пристрої з фіксацією конфігурації та версії застосунку.

**Як перевірити.** Підготувати 100 записів. На одному пристрої зафіксувати конфігурацію, п’ять разів відкрити екран списку й записати тривалість кожного вимірювання. Кожне значення має бути не більше 2 с.

## Висновок

Уточнено всі вісім вимог і сценарії їх перевірки. Прибрано дублювання щодо показу статусу, доповнено правила валідації та описано випадки порожнього списку й однакових дат. Вимоги збережено під тими самими ідентифікаторами. Чотири функціональні й дві нефункціональні вимоги належать до MVP, дві залишено для наступних версій.
